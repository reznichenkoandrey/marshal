# Plan runner: план, що виконується вночі (#278)

Статус: Етапи 0–2 написані (`desktop/plan-runner/`). Етап 2 підключений до застосунку: opt-in `planRunnerEnabled`, голос `./marshal do plan …`, лише вже відкриті сесії, `report.md` і `run.log`; наживо ще не перевірений. Етапи 3–6 — попереду. Epic #275, Phase 4.
Залежності: реєстр сесій (#262, `desktop/claude-code/registry.ts`), hooks (#263, `hooks-controller.ts`), usage (#268, `statusline.ts`), voice-диспетчер (#318, `desktop/assistant/dispatcher.ts`).

## 1. Проблема

Власник складає план на кілька кроків, його виконують сесії Claude Code, а сам він спить або відійшов. Вранці потрібен звіт: що зроблено, що зламалося, що чекає відповіді. Кожен крок лишається у звичайній сесії, тож його можна переглянути й перезапустити руками.

Жорстка межа з `CLAUDE.md`: runner ніколи не пушить, не мерджить, не деплоїть і не видаляє гілки. Це рішення власника, не технічне обмеження.

## 2. Модель плану

План — це файл, не запис у базі. Зберігання: `<userData>/plans/<planId>/plan.json`, звіт `report.md` поруч. Жодного Python і жодної БД. Кожна зміна стану пишеться на диск одразу, тож після краху або сну Marshal продовжує з останнього стану.

```json
{
  "id": "2026-11-21-deps",
  "title": "Оновити залежності і прибрати dead code",
  "project": "/Users/…/htdocs/marshal",
  "lanes": [
    { "id": "A", "session": "marshal-runner-A", "source": "existing" },
    { "id": "B", "session": "marshal-runner-B", "source": "new" }
  ],
  "steps": [
    {
      "id": "s1",
      "lane": "A",
      "text": "Онови devDependencies і запусти npm run check",
      "dependsOn": [],
      "check": "npm run check проходить",
      "notBefore": null,
      "state": "pending"
    }
  ],
  "limits": { "maxFixRounds": 2, "maxWallMinutes": 480, "stopAtUsagePct": 97 }
}
```

- **lane** — одна сесія Claude Code. Крок однієї лінії виконується строго по черзі. Дві лінії працюють паралельно, лише якщо їхні кроки не залежать одне від одного.
- **source** — `existing` (сесія вже відкрита, runner знаходить її в реєстрі за ім'ям) або `new` (runner сам запускає сесію через той самий шлях, що `./marshal spawn`).
- **check** — умова готовності, яку runner передає в промпт кроку разом із текстом. Не виконується runner-ом сам.
- **notBefore** — час, раніше якого крок не стартує. Працює лише коли Mac прокинувся (див. розділ 6).
- **state** — `pending | running | blocked | question | failed | held | done | skipped`.

### Створення плану

1. Голосом: «склади план на ніч» → диспетчер збирає кроки з діалогу (через `./marshal ask`, уже є).
2. Вручну: текстовий файл або панель (окрема задача, поза цією специфікацією).
3. З sub-board мозкового штурму (#276) — пізніший етап.

На створенні кожен текст кроку перевіряється. Якщо крок просить `push`, `pull`, `rebase`, `merge`, `deploy`, `delete` гілки або `reset --hard` — план відхиляється з поясненням, який крок і яке слово. Це лише перший бар'єр, другий — hook (розділ 4).

## 3. Запуск

- `plan run <id>` через голос або панель. Перший запуск фіксує `runStartedAt` і створює worktree на кожну лінію (розділ 4).
- Для `source: "new"` runner використовує `claude --name <session>` у тому ж хості, що `assistantTerminalHost` (Harbor, Terminal). Чекає появи сесії в реєстрі до 45 с, як `SPAWN_WAIT_MS` у `dispatcher.ts`.
- **Сесії Claude desktop runner не створює і не вбиває.** Deep link `claude://code/new` (`desktop-session.ts`, `newSessionUrl`) відкриває сесію, але Marshal не має каналу, яким її можна стежити, зупинити чи перезапустити — так само як у `reply.ts` і в правилі #437. Лінії runner-а мають бути в Terminal або Harbor. Desktop-сесію можна підключити як `existing`, тільки для кроків, що не потребують стеження за завершенням.

### Tick

Tick — функція без побічних ефектів: `(стан плану, факти з реєстру і hooks, usage) → список дій`. Лише вона тестується unit-тестами. Виконує дії окремий шар.

Tick запускається на подіях, а не таймером:
- Stop hook сесії лінії (крок завершився);
- Notification hook (permission prompt → `blocked`);
- зміна статусу в реєстрі (`busy → idle`);
- зміна usage у statusline (#268);
- спрацювання `notBefore`.

Один таймер на 60 с дозволено лише поки план у стані `running`, і він зупиняється з виходом із цього стану. Так вимога #281 про відсутність поллерів у простої не порушується: план, що працює, — не простій.

Крок стартує, лише коли одночасно:
1. всі `dependsOn` мають `done`;
2. сесія лінії в статусі `idle` (`describeStatus`, `registry.ts`);
3. usage 5 год < `stopAtUsagePct` (97%);
4. `notBefore` минув або `null`;
5. немає відкритого питання цієї лінії.

Повторна відправка: якщо після відправки сесія не перейшла в `busy` за 30 с — повторити один раз. Далі крок `failed` з причиною `not-picked-up`.

## 4. Ізоляція: worktree на кожну лінію

Кожна лінія працює у власному worktree, створеному від `main`:

```
git worktree add <repo>/.claude/worktrees/plan-<planId>-<lane> -b plan/<planId>-<lane> main
```

- Гілки `plan/…` локальні. Runner їх не пушить і не відкриває PR.
- Worktree живе в `.claude/worktrees/`, тож не потрапляє в git (правило `.claude/` з `CLAUDE.md`).
- Скрипти і скріни — у `~/Screenshots/<project>/`, не в worktree.
- Після плану власник сам вирішує: змерджити гілку, переглянути, викинути. Runner тільки створює worktree і лишає його; видаляє лише після явного `plan clean <id>`.
- Проблема: worktree від `main` не бачить незакомічених змін власника. Опис плану має містити `base` — гілку або коміт. За замовчуванням `main`, і runner відмовляється стартувати, якщо `base` не існує.

Hook-guard для сесій runner-а (`.claude/settings.json` лише всередині worktree, не в репо): `PreToolUse` блокує `git push`, `git reset --hard`, `git clean`, `git branch -D`, `rm -r`, `git merge`, `git rebase`. Скрипт guard-а — окремий `.sh` у `<userData>/plans/guard/`, того ж типу, що `marshal-claude-hook.sh`.

## 5. Результат кроку, поразки і питання

### Маркер результату

Промпт кроку закінчується вимогою: останній рядок відповіді — `PLAN-STEP <id кроку>: done|failed|question`. Id кроку в маркері потрібен, щоб запізніла відповідь на попередній промпт не закрила наступний крок.

- Маркер є → рішення беремо з нього.
- Маркера немає → мала модель класифікує відповідь (той самий провайдер, що summary, `resolveSummaryProvider`). Модель не отримує права щось схвалювати: лише `done | failed | question`.

### Fix rounds

- `failed` → до `maxFixRounds` (2) повторних спроб у тій самій сесії з промптом «виправ і повтори check».
- Вичерпано → крок `failed`, усі кроки, що від нього залежать, отримують `held` (propagation через граф `dependsOn`, сам крок не перезапускається).
- Інші лінії, що не залежать від held-кроку, працюють далі.

### Блокування на permission prompt

Notification hook з `waitingFor: "permission prompt"` (уже є в `registry.ts`) → крок `blocked`, runner нічого не відповідає. Власник отримує нотифікацію і голосову фразу, як у #375. Продовження — лише після того, як власник відповів (через `./marshal reply`, `reply.ts`). Runner ніколи не натискає Return на діалозі.

### Питання під час відсутності власника

- `PLAN-STEP <id>: question` → крок `question`, питання записане в `report.md`.
- Модель може відповісти **лише** якщо відповідь буквально є в тексті плану. Ніякого «здогаду». Вона не може схвалити push, merge, deploy чи delete за жодних обставин: такі питання завжди чекають власника.
- Інакше питання чекає ранку.

## 6. Mac має не спати

Це найслабше місце всієї ідеї. План на 6 годин не виконається, якщо Mac заснув.

- `caffeinate -i -w <pid Marshal>` на час `running`. Блокує idle-sleep, поки живе Marshal. Це покриває відхід від клавіатури з увімкненим живленням.
- **Закрита кришка на батареї** — `caffeinate -i` не допомагає, Mac засне. `caffeinate -s` працює лише на зовнішньому живленні (AC). Тому runner **не стартує** на батареї, поки власник явно не підтвердив, і попереджає, що план зупиниться після закриття кришки.
- Системні налаштування (`pmset`, сон, розклад пробудження) Marshal не змінює: потребує sudo і є налаштуванням системи. Лише повідомлення з точною командою для власника, якщо він хоче.
- Відновлення після сну: стан на диску → після пробудження tick продовжує. Сесії, що зникли, — `source: "new"` запускається знову, `existing` позначається `failed: session-gone`.
- `notBefore` після сну запускається із запізненням. Це треба сказати власнику в звіті, а не мовчки.
- Мережа і Anthropic API можуть бути недоступні: провайдер-помилка = крок `failed` з причиною `provider`, не fix round.

## 7. Ліміти витрат

- **5 год usage ≥ 97%** → tick не стартує нових кроків. Немає запуску нових кроків при зупинці (`stopAtUsagePct`).
- **`maxWallMinutes`** (за замовчуванням 480) → план ставиться на паузу з позначкою в звіті.
- **`maxFixRounds`** (2) — обмежує кількість повторних спроб, а з ними й вартість кроку.
- Вартість по кроку береться з statusline (#268), пишеться в `report.md`. Немає ліміту в доларах — є ліміт у відсотках usage, бо саме його Claude Code показує.
- Малі моделі для класифікації маркера і відповідей на питання рахуються окремо в звіті, щоб вартість runner-а не ховалась.

## 8. Звіт

`report.md` оновлюється на кожному переході стану. Вранці — один файл:

- план, база, гілки worktree;
- таблиця кроків: стан, лінія, fix rounds, вартість;
- `held` і їхня причина;
- питання, що чекають власника;
- час простою і запізнілі `notBefore`.

Голосом: «статус плану», «пауза», «звіт». Ті самі слова приймає диспетчер.

## 9. Поетапна доставка

Кожен етап — окремий PR, зелений `npm run check` і перевірка, описана в колонці «Готово коли».

| Етап | Що | Готово коли |
|---|---|---|
| 0 | Чисте state machine: tick, залежності, idle/usage gating, fix rounds, hold propagation, правило питань | Unit-тести на фікстурах, без Electron і без сесій |
| 1 | Зберігання плану (`plan.json`, відновлення після краху), валідація, відхилення небезпечних кроків | Тести валідації і відновлення зі зламаного файлу |
| 2 | Запуск на вже відкритих сесіях (`existing`), без worktree, без спавну | 3 кроки, 2 реальні сесії, звіт записано |
| 3 | Worktree-ізоляція, `source: "new"`, hook-guard | Гілки `plan/…` створені, `git push` у guard-і блокується |
| 4 | Маркер `PLAN-STEP`, класифікатор, fix rounds, `blocked` по permission prompt | Навмисно зламаний крок дає `held` у звіті |
| 5 | Питання, модель-відповідь за правилом, голос, панель | Питання про push ніколи не відповідається моделлю |
| 6 | `caffeinate`, `notBefore`, відновлення після сну, батарея | Ручний прогін на AC; на батареї — відмова з поясненням |

Критерій «Done» з issue (3 кроки над двома реальними сесіями, звіт записано) виконується після етапу 4. Етап 0 дає лише тестовану логіку tick-а.

## 10. Відкриті питання

1. **Режим дозволів сесій runner-а.** `bypass` вночі небезпечний, `auto` може зупинятися на першому prompt-і і стояти до ранку. Пропозиція: `auto` + guard-hook з розділу 4. Потребує рішення власника.
2. **Desktop-сесії.** Чи можна дозволити `existing` desktop-сесію для кроків без стеження, або заборонити повністю? Пропозиція: заборонити для Етапу 2–4.
3. **Модель класифікатора і відповідей.** Чи дозволено надсилати текст плану й відповіді сесій малій моделі (локальний провайдер summary)? За замовчуванням — так, як у summary.
4. **Паралельні лінії.** Скільки максимум? Пропозиція: 2, бо usage-ліміт спільний для всіх сесій.
5. **Джерело плану з boards (#276).** Формат sub-board ще не визначено; до цього план створюється голосом або файлом.
6. **Кришка на батареї.** Прийнятна відмова на батареї, чи власник хоче запуск з попередженням?
7. **Видалення worktree.** Власник чистить руками чи через `plan clean`? Пропозиція: `plan clean`, який вимагає підтвердження, як і всі видалення.
8. **Головна невідома — надійність `PLAN-STEP`.** Чи дотримується Claude Code маркера в останньому рядку стабільно? Перевіряється лише на Етапі 4 наживо; класифікатор — страховка, не основний механізм.
