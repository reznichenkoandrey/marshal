# Live data dashboards за голосом — spec (#279)

Refs #279 · epic #275 · Phase 4 · пов'язано: #280 (scheduled workflows), #276 (voice boards), #281 (бюджет ресурсів), #396/#398 (Lumen-дашборди).

Це spec, без коду. Мета — зафіксувати джерела даних, модель оновлення, місце показу, вартість у пам'яті і поетапну доставку, щоб наступні PR були списком задач, а не новим дослідженням.

## 1. Що має бути

Команда «побудуй графік реєстрацій за тиждень по днях» або «порівняй latency перекладача за бекендами» дає живий дашборд з реальних даних. Дашборд:

- читає дані тільки з read-only джерел;
- показується швидко: спершу скелети карток з назвами, потім кожен графік заповнюється, коли його запит повернувся;
- редагується наступною фразою («додай порівняння з минулим тижнем»), і графіки, яких модель не чіпала, не перезапитуються;
- зберігається як шаблон і відкривається голосом;
- не оновлюється сам у фоні, поки вікно закрите.

Мова запиту, назв і підписів — за мовою запиту (`uk` / `en` / змішана), як у #279 і в epic.

## 2. Джерела даних

| Джерело | Як підключено | Read-only гарантія | Потрібен setup |
|---|---|---|---|
| Postgres | Settings → Data sources: URL, файл 0600 у `<userData>`, не в `settings.json`, не в лог | `psql` + read-only роль + `default_transaction_read_only=on` + `statement_timeout` + один statement | так, URL |
| Аналітика (PostHog тощо) | існуючий MCP-конектор | тільки read-tools у allowlist | так, OAuth через /mcp |
| Git history | `git log` / `git shortlog` у вибраній теці | команди без записів, лише allowlist (`log`, `shortlog`, `rev-list`) | ні |
| GitHub | `gh` (issues, PR, `--json`) | лише `gh api` GET / `gh pr list` / `gh issue list` | ні, якщо `gh auth` уже є |
| Marshal history | `<userData>/capture-history`, `meetings/`, `command-log.json`, `claude-code/dossiers.json` | читання файлів у main, без SQL | ні |

Кожне джерело — окремий канал до моделі. Варіант «кожне джерело = окремий stdio MCP-сервер» із #279 працює, але з однією поправкою: процес стартує **на час побудови або оновлення дашборда** і гаситься після. Постійно живий MCP-процес на джерело — це idle-витрата, яку #281 не дозволяє. Альтернатива без MCP: main сам виконує запит через allowlist і віддає моделі вже CSV. Рекомендація — **main виконує, модель не має прямого доступу до джерела**. Тоді read-only правило живе в одному місці (main), а не в кожному MCP-сервері.

### Postgres: read-only у три шари

`default_transaction_read_only=on` — це лише перший шар. Його можна скинути `SET`-ом у самому запиті, тому ланцюжок такий:

1. **Роль.** Рекомендований setup — окрема роль з `GRANT SELECT` лише на потрібні схеми. Маркетинг-SQL не отримає права на запис, навіть якщо guard зламано. Marshal пише в Settings підказку, як створити роль, але не створює її сам.
2. **Guard у main.** Перед `psql` перевірка тексту:
   - рівно один statement (крапка з комою в кінці дозволена, інші — ні; рядки в лапках і коментарі парсяться, а не шукаються регулярним виразом);
   - перший токен — `SELECT`, `WITH`, `VALUES` або `TABLE`;
   - заборонені ключові слова навіть усередині CTE: `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `GRANT`, `COPY`, `SET`, `RESET`, `CALL`, `DO`, `LOCK`, `VACUUM`, `REFRESH`;
   - `SELECT … INTO` заборонено.
3. **Сесія `psql`.** `-v ON_ERROR_STOP=1`, `-c "SET default_transaction_read_only = on; SET statement_timeout = '15s';"` перед запитом, вивід `--csv` з обрізанням на ~20 KB (за байтами, з позначкою `truncated`), `--no-psqlrc`, пароль через `PGPASSFILE` або env, а не в argv (argv видно в `ps`).

Відомі межі, які spec визнає: деякі функції (наприклад `dblink`, `pg_sleep`) не блокуються `read_only` так, як очікує наївний guard. Тому роль із `SELECT`-only і відсутність `dblink` у `search_path` ролі — обов'язкова умова, а не побажання. Guard — друга лінія.

Чому `psql`, а не Node-драйвер `pg`: не треба нової залежності, `psql` вже є в більшості Postgres-установок і лишається зовнішнім бінарником, як `gh` і `git`. Якщо `psql` немає — стан джерела `missing` з підказкою, як у #416 для хаба. Відкрите питання — чи брати `pg` (чистий JS, але +залежність і ще одна бібліотека в бандлі). Рекомендація: `psql` на старті, `pg` тільки якщо `psql` виявиться обмеженням.

### Аналітика через конектор

Конектор уже живе в Claude-сесії, а не в Marshal. Варіанти:

- **A (рекомендовано для першої версії):** не підключати конектор до Marshal. Дашборд з аналітики — лише з CSV, який користувач сам експортував у теку, видиму для дашборда. Нуль нових credentials.
- **B:** Marshal викликає MCP-конектор через `agent/` backend з allowlist read-tools. Це вимагає, щоб конектор був авторизований у цьому контексті, інакше — OAuth через /mcp, якого Marshal сам не запускає.

Рішення за A або B — відкрите питання, бо B тягне залежність від стану чужого OAuth.

## 3. Протокол моделі: план, потім графіки, потім keep

Модель відповідає потоком рядків-подій (NDJSON), щоб UI рендерив скелети одразу:

```
{"type":"plan","charts":[{"id":"c1","title":"Реєстрації по днях","kind":"line","source":"pg:prod"}, …]}
{"type":"query","id":"c1","sql":"SELECT …"}
{"type":"keep","id":"c3"}
{"type":"title","value":"Реєстрації за тиждень"}
```

- `plan` приходить першим. Скелети карток видно за секунди, ще до першого запиту.
- `query` — тільки SELECT через guard з розділу 2. Main виконує, кладе CSV в кеш, шле `chart-data` у renderer.
- `keep` — графік лишається як є в follow-up і **не перезапитується**. Немає `keep` — графік вважається змінним, але дані з'являться лише після `query`.
- Парсер — чиста функція з тестом: порожній рядок, сміття між рядками, `query` без `id`, `keep` для невідомого `id`, рядок більший за ліміт (наприклад 64 KB), незнайомий `type` ігноруються з лог-рядком, а не валять побудову.

Ліміти: максимум 8 графіків на дашборд, максимум 1 запит на графік на побудову, таймаут на весь build (наприклад 3 хвилини), після якого залишене зі скелетом позначається `timeout`.

Модель-бекенд — той самий, що для диспетчера/summary (`agent/`), окремого SDK-клієнта не додаємо.

## 4. Модель оновлення: лише за подією

Жодних таймерів і polling у простої. Дашборд оновлює дані в чотирьох випадках, і тільки в них:

1. **Відкриття вікна дашборда** — оновлення запитом користувача або тим, що вікно відкрилось. Показуємо кеш з позначкою «оновлено N хв тому», оновлюємо лише протухлі графіки (поріг — поле `ttl` у шаблоні, за замовчуванням 0, тобто «завжди при відкритті»; це рішення відкрите).
2. **Кнопка Refresh** у вікні.
3. **Голосова фраза** «онови дашборд реєстрацій» — той самий шлях, що й кнопка.
4. **Scheduled workflow (#280)** — оновлює дашборд за розкладом, але розклад живе в #280, а не тут. Дашборд не має власного cron.

Заборонено: таймер «кожні 5 хвилин», polling БД, оновлення у фоні при закритому вікні, «refresh on focus», що стріляє на кожну зміну фокуса.

Стан «протухло» показується тільки як текст у картці (`оновлено 3 год тому`), без анімації й без фонових перевірок.

Кеш результатів — у `<userData>/dashboards/<id>/`: `dashboard.json` (план, SQL, посилання на джерело — без паролів) і `data/<chart-id>.csv` з обрізанням до 20 KB. Сам SQL зберігається, щоб шаблон можна було перезапустити; URL джерела — ні, лише `source.id`, а URL лежить у 0600-файлі.

## 5. Де живе дашборд

Варіанти:

- **A. Вкладка в home (#284).** Home — єдине вікно асистента з dock і summary. Дашборд там тісний: home 1100×720, а графіки потребують ширини. Плюс home вже несе strip, візуал, сесії. Не рекомендовано.
- **B. Окреме вікно «Dashboards»** за шаблоном `meeting-history` / `capture-history`: один `BrowserWindow`, створюється при відкритті, знищується при закритті, використовує `dashboard.css` (`.shell`, `.block`, `.metric-row`, `.card`) без копіювання. **Рекомендовано.**
- **C. Окреме вікно на кожен дашборд.** Гарно для презентації, але кожне вікно — ще один GPU-пул Chromium (див. #310) і ще один процес. Не на старті.

Рекомендація — B. Home отримує лише картку «Dashboards» з лічильником і кнопкою «відкрити»; сам дашборд — у своєму вікні. Голосовий шлях: `./marshal do dashboard <назва>` відкриває шаблон.

Вікно — content-protected? Дашборд може показувати рядки з прод-БД. Рекомендація: **так**, як у #285 і субтитрів, щоб не злити дані в screen share. Це відкрите питання для owner, бо не всі дашборди приватні.

Board/presenter-режим (#276) — окремий режим того самого вікна, а не третє вікно. Світла тема лишається опцією для проєктора, як сказано в issue.

## 6. Рендер графіків

Жодних chart-бібліотек. У `dependencies` зараз немає жодної (`@anthropic-ai/sdk`, `dotenv`, `ffmpeg-static`, `ical.js`, `onnxruntime-web`, `playwright`, `uiohook-napi`), і додавати Chart.js (≈200 KB, ще й свій canvas) заради line/bar/area — зайве.

Рекомендація: inline SVG, генерується в renderer з чистих функцій (`desktop/renderer/dashboard-charts.js`, тестується без Electron), кольори — тільки токени (`--state-*`, `--accent`), жодного hex. Підтримувані типи в першій версії: line, bar, area, stacked. Legend-перемикання — клік по легенді, що ховає серію. Brush-zoom, comparison series і event marks — пізніші етапи, бо потребують вже стабільного рендера.

Статистика (min / max / avg) рахується в main з CSV або в чистій функції, не в DOM.

Межа ponytail: якщо плавний зум і тултіпи знадобляться у 3+ місцях, тоді вибирати бібліотеку. Зараз — ні.

## 7. Ресурси і бюджет (#281)

Idle (вікно закрито, дашборд не будується): **0 MB** на нову фічу. Немає таймерів, немає процесів, немає watcher-ів. Збереження в `<userData>` — лише JSON і CSV на диску.

Вікно відкрите, без побудови: одне `BrowserWindow` з SVG. Оцінка — порядок ~30–40 MB renderer + GPU-пул, як у інших вікнах (#310). Перевірити `npm run perf:footprint` з відкритим дашбордом і з закритим, щоб не змішувати з home-віджетом.

Побудова (короткочасно):

- `psql` — один процес на запит, порядок 5–10 MB, живе до відповіді або `statement_timeout` (15 s), далі гаситься.
- `git` / `gh` — короткі процеси.
- Модель — той самий backend, що вже в пам'яті, або on-demand.
- Жодного Python. Жодного локального LLM.

Дискові ліміти: кеш до 20 KB на графік, до 8 графіків на дашборд, до 50 шаблонів — разом ≤ ~8 MB. Ретенція: шаблон без відкриття 90 днів — позначається, не видаляється без підтвердження (видалення — лише за словом власника).

Заміри, які треба записати в PR кожного етапу: idle з закритим дашбордом, відкрите вікно без побудови, пік під час побудови на 3 графіки.

## 8. Безпека і приватність

- URL Postgres — 0600, не в лог, не в `settings.json`, не в transcript. Помилка `psql` йде в лог **без** рядка підключення (за аналогією з календарною адресою #269: тільки тип помилки).
- Рядки з БД йдуть моделі для побудови графіка. Це дані, які покидають Mac, тож перед першим джерелом Postgres користувач має підтвердити це явно (окремий прапорець у Settings: «дозволити надсилати результати запитів моделі»). Без прапорця модель отримує лише схему (імена таблиць і колонок), не рядки. Це відкрите питання для owner: чи достатньо схеми для більшості запитів.
- SQL, який виконує модель, видно в UI перед або одразу після виконання. Жодного прихованого виконання поза тим, що видно.
- Guard — тестований окремо (розділ 9).

## 9. Тести, які мають пройти до «Done»

З issue: read-only enforcement (multi-statement, write-statements, timeout, cap), parser протоколу plan/keep. Додатково:

- guard відхиляє `WITH x AS (DELETE …) SELECT`, `SELECT 1; DROP …`, коментарі з `;` всередині рядків;
- парсер NDJSON переживає обрізаний рядок посеред JSON;
- `keep` не викликає `query` у наступному build;
- CSV-обрізання на межі UTF-8 символа не ламає кодування (кирилиця).

Побудова на реальній Postgres і на історії git — ручний прогін перед merge етапу 2 і 1 відповідно, не CI (бюджет GitHub Actions на приватних репо обмежений).

## 10. Поетапна доставка

**Етап 0 — pure layers (найменший PR).** Guard SQL, парсер NDJSON, статистика, SVG-розрахунки, сховище шаблонів (JSON) — з тестами, без UI і без мережі. Залежить тільки від себе.

**Етап 1 — git і GitHub джерела + вікно.** Джерела `git` і `gh`, `dashboard-window.ts` на `dashboard.css`, inline SVG line/bar, Refresh, побудова через модель з `plan`/`query`/`keep`. Жодного Postgres, жодних паролів. Це найбезпечніший спосіб перевірити всю ланку.

**Етап 2 — Postgres.** Settings → Data sources, 0600-файл, `psql`, read-only роль, прапорець «надсилати результати моделі», підказка для створення ролі. Ручна перевірка на реальній БД owner.

**Етап 3 — шаблони і голос.** Збереження як шаблон, `./marshal do dashboard <назва>`, фраза «онови дашборд…», Marshal-історія як джерело.

**Етап 4 — розширення.** Scheduled refresh через #280 (тільки тут з'являється розклад), аналітика через конектор (варіант B, після рішення), export у self-contained HTML/PDF, board-режим #276, brush-zoom і comparison series.

Кожен етап — окремий PR з замірами футпринта в описі.

## 11. Відкриті питання для owner

1. **`psql` чи Node-драйвер `pg`?** Рекомендація — `psql`, поки не буде обмеження.
2. **Чи надсилати рядки результатів моделі, чи лише схему?** Рекомендація — лише схему за замовчуванням, рядки за окремим прапорцем на джерело.
3. **Аналітика: CSV-експорт (A) чи конектор у Marshal (B)?** Рекомендація — A для етапу 1–3.
4. **Вікно дашборда content-protected за замовчуванням?** Рекомендація — так.
5. **`ttl` шаблону за замовчуванням: 0 (оновлювати при кожному відкритті) чи, наприклад, 1 година?** Рекомендація — 0: без таймера це дешево, а старі дані гірші за зайвий запит.
6. **Чи потрібна окрема роль Postgres, чи досить `default_transaction_read_only`?** Рекомендація — роль обов'язкова; `default_transaction_read_only` лише як додатковий шар.
7. **Скільки джерел максимум?** Пропозиція — 5 Postgres-джерел, щоб Settings не ставав таблицею.

## 12. Що не робимо

- Не пишемо в БД ні за яких умов, навіть з явним підтвердженням. Write-доступ — це інший spec.
- Не додаємо chart-бібліотеку на старті.
- Не тримаємо MCP-процеси джерел живими між побудовами.
- Не оновлюємо дашборд у фоні і не полимо БД.
- Не копіюємо `dashboard.css`, а використовуємо його класи.
