# Speaker check: ігнорувати мову не власника (#287)

Статус: етап S0 зроблено (`desktop/assistant/speaker/calibration.ts`, `tests/speaker-calibration.test.ts`); S1–S4 не починались, рішення S0 — у §13. Опційна фіча, Phase 5 епіку #275. Залежить від #281 (бюджет ресурсів) і #274 (фраза активації). Цей документ — рішення для власника перед будь-якою реалізацією.

## 1. Проблема

Фраза активації (#274) і будь-який режим «слухаю без клавіші» ловлять чужу мову: телевізор, колегу в кімнаті, співрозмовника на дзвінку. Зараз захист — лише назагал:

- `isOnCall` (`desktop/presence/call-presence.ts`) вимикає wake, коли інший процес тримає мікрофон. Це ловить дзвінки, але не людей у кімнаті і не відео з динаміків.
- Ім'я на початку речення (`wakeCommand`, `desktop/assistant/wake/wake-listener.ts`) відсіює «маршрут» і «martial», але не голос.

Speaker check додає: команда без клавіші приймається, лише якщо голос схожий на голос власника.

## 3. Наявний стан, на який спирається дизайн

- `desktop/assistant/wake/wake-listener.ts` — два engine: `apple` (macOS 26+, `speech-wake.swift`, SpeechAnalyzer) і `sherpa` (KWS, `wake-listener.swift`). **Важливо:** `apple` віддає лише текст. Аудіо-кліпа немає, тож ембеддингу зняти не з чого. Sherpa пише WAV-кліп (`clip <path>`) і вже має шлях до whisper.
- `desktop/dictation/dictation-service.ts` — PTT-записи мають WAV. Вони є природними позитивними прикладами власника для shadow-режиму.
- `desktop/assistant/wake/sherpa-kws.h` — копія структур C API sherpa-onnx v1.13.8, підключається через `dlopen`. Той самий runtime може дати speaker embedding, якщо в API v1.13.8 є потрібні структури (перевірити, не припускати).
- `desktop/assistant/features.ts`, `desktop/perf/footprint.ts` — місце для нового рядка стану і заміру.
- `onnxruntime-web` уже в залежностях (Silero VAD у captions). Це варіант без нового рантайму.

## 4. Варіанти

### A. On-device speaker embedding (ECAPA / ResNet / CAM++-клас ONNX)

Модель видає вектор фіксованої довжини з короткого кліпа. Схожість із профілем власника — косинус. Поріг вираховується з власних балів.

- Плюси: найкраща точність з відомих; працює при відносно коротких кліпах (2–4 с); тренована на multi-speaker даних, тож не залежить від мови власника.
- Мінуси: ще одна модель (порядку 20–30 МБ, точний розмір залежить від обраної, перевірити); фічі (fbank) треба рахувати так само, як при тренуванні.
- Рантайм: два шляхи.
  - A1. **sherpa-onnx speaker extractor** через той самий `dlopen`. Нуль нових рантаймів. Ризик: структури C API треба додати в header, як для KWS.
  - A2. **onnxruntime-web** (уже є). Фічі — JS-код або окремий WASM. Більше своєї логіки, але без нового native-шару.

Рекомендація: A1, якщо header v1.13.8 має API speaker embedding. Якщо ні — A2. Рішення після S1 (spike).

### B. Голосовий профіль через явну реєстрацію (enrollment)

Власник записує 10–30 с (як «Add voice from recording» для Holos). Профіль = ембеддинг із цього запису.

- Плюси: зрозумілий і контрольований; не треба чекати shadow-накопичення; простіше тестувати.
- Мінуси: ритуал, який issue явно відкидає («no enrolment ritual»). Один запис не покриває зміну голосу, мікрофон, AirPods.

Може бути **доповненням** до A, а не окремим варіантом: explicit кнопка як запасний шлях, пасивне навчання як основний.

### C. Без перевірки голосу

- Залишаємо `isOnCall` і вимогу імені на початку речення. Чужий голос з динаміків лишається проблемою.
- Плюс: нуль ресурсів, нуль ризику помилкового відсіювання.
- Мінус: закриває лише дзвінки, не кімнату.

Варіант C — розумний fallback, якщо A не проходить бюджет (R6). Його не треба вилучати з дизайну.

### Порівняння

| Критерій | A1 sherpa | A2 onnxruntime-web | B enrollment | C none |
|---|---|---|---|---|
| Новий рантайм | ні | ні | — | — |
| Нова модель | так (~20–30 МБ) | так | так (та сама) | ні |
| Точність | висока | висока | середня (один запис) | — |
| Ритуал | ні | ні | так | ні |
| Складність коду | середня | вища (fbank у JS) | низька | нуль |
| Ризик для бюджету | середній | середній | той самий | нуль |

## 5. Калібрування і дані

Issue пропонує синтетичні чужі голоси (нативні TTS macOS, укр. і en). Це корисно як стартова точка, але має межу:

- TTS не має реверберації, шуму кімнати, кодека AirPods, відстані до мікрофона. Поріг, виміряний на TTS, буде оптимістичним у кімнаті.
- Позитивні приклади власника беруться з PTT (чистий голос, близько до мікрофона). Це інше розподілення, ніж wake з відстані.

Тому для «Done when» потрібен реальний набір: 20–30 хв записів власника (тихо, з відстані, з AirPods), 20–30 хв чужої мови в кімнаті і телевізора. Записи — поза репо, у `~/Screenshots/marshal/speaker-samples/` або userData, не в git.

Пороги: поріг = нижній перцентиль власних балів мінус запас (як у issue). Перцентиль і запас — параметри калібрування, не константи в коді.

## 6. Ресурси

Оцінки, не заміри. Всі числа підтвердити S1.

- Диск: модель ~20–30 МБ у `<modelsDir>/speaker/`, поза бандлом.
- RAM: модель + runtime ~40–70 МБ, коли завантажена.
- CPU на перевірку: ~20–60 мс на кліп 2–4 с (оцінка для CPU ONNX).
- Холодний старт: ~0.5–1.5 с (оцінка). Це додається до команди, якщо модель вивантажена.

Проти бюджету (R6): idle із wake зараз ~163–262 МБ (`#350`, `#308`, сама фіча wake +43 МБ). Резидентна модель понад 60 МБ може вийти за 300 МБ. Тому:

- **Завантаження за кандидатом:** модель піднімається, коли wake-spotter (або Apple engine) дав кандидат. Вивантажується через 2 хв без кандидатів. У простої резидентної моделі немає, як і в Holos і whisper-server.
- Наслідок: перша команда після тиші на ~0.5–1.5 с довша. Ціна відома; питання 4 в §9.

Аудіо-буфер: кільцевий буфер 3–4 с у пам'яті (для Apple engine — новий, §7). Пам'ять невелика, але треба заміряти разом із footprint.

Ембеддинг власника зберігається як один вектор (кілька KB), калібрування — JSON кілька рядків.

## 7. Зміни в Swift для Apple engine

Apple engine (default на macOS 26+) передає лише текст. Щоб порахувати ембеддинг, потрібен аудіо-кліп для кожного кандидата.

Варіант 1 (рекомендовано): `speech-wake.swift` тримає кільцевий буфер PCM 16 kHz mono. Коли `wakeCommand` бачить ім'я, helper пише кліп (як `clip <path>` у sherpa). Зміна невелика, але торкається helper-а, який зараз перевірений (#432).

Варіант 2: для Apple engine перевірку вимкнено і показано, що вона недоступна. Простіше, але default-шлях на macOS 26+ не отримує фічі.

Рішення потрібне до старту S3, не зараз.

## 8. Build vs buy

- **Buy, хмарна верифікація голосу** (Azure, Google, інші): відхилено. Аудіо покидає пристрій, порушує R3.
- **Buy, локальний SDK** (комерційні бібліотеки типу Picovoice Eagle): потребують акаунта, ключа доступу і ліцензії з обмеженнями. Не перевірено тут — вартість і умови треба звірити окремо, якщо власник хоче цей шлях. Додає залежність, яку важко вимкнути.
- **Build на sherpa-onnx (A1)**: той самий runtime, що wake; мінімум нового коду; open-source.
- **Build на onnxruntime-web (A2)**: без нового native; більше власного коду (fbank, нормалізація).

Рекомендація: build, A1 з fallback на A2. Вибір зробити після S1.

## 9. Відкриті питання для власника

1. **Зона дії:** лише wake-команди, чи також follow-up (6 с після «Слухаю.») і відповіді на `askOwner`? Пропозиція: wake і follow-up; відповіді на питання не перевіряти, бо Marshal сам запитав.
2. **Невпевнений голос:** мовчки відсіяти, чи сказати «не впізнаю голос»? Мовчки безпечніше для сну; голосом зрозуміліше, але сам це створює шум у кімнаті.
3. **Навчання:** лише пасивне (PTT-записи), чи є кнопка «Записати мій голос» як запасний шлях (варіант B)?
4. **Затримка:** прийнятні 0.5–1.5 с до першої команди після тиші, якщо модель вивантажена? Або модель резидентна, поки wake увімкнено (+40–70 МБ)?
5. **Профілі по пристроях:** один профіль на всі мікрофони чи окремий для AirPods і MacBook? Пропозиція: один, з можливістю додати другий пізніше.
6. **Синтетичні негативи:** дозволити TTS як стартову калібровку з позначкою «оптимістично», чи лише реальні записи кімнати?
7. **Змішана мова:** власник говорить uk і en в одному реченні. Моделі тренувалися переважно на en; треба перевірити на власних записах uk. Це ризик для точності, не для архітектури.
8. **Ціль помилок:** що важливіше — не реагувати на чужого (false accept) чи не втратити свою команду (false reject)? Від цього залежить запас порогу.
9. **Feedback:** правило «команда повторена за 15 с → поріг вниз» з issue шумне: людина може повторити з інших причин. Погоджуєтесь на підтвердження (лише явна «так, це я»), чи лишаємо пасивне?
10. **Повторне навчання** після тижня без хибних відмов: автоматично, чи лише кнопкою?

## 10. Поетапна доставка

Кожен етап має вихід, який можна перевірити без наступного.

- **S0. Дані і калібрування (чистий код, без runtime).** Модуль порогів: перцентиль, запас, рішення accept/reject, feedback-правило, тихий-голос фільтр. Тести на синтетичних балах. Вихід: `calibration` тестований. Власник записує реальні семпли (§5).
- **S1. Spike рантайму.** Підключити speaker extractor (A1 або A2) у ізольованому скрипті. Виміряти: розмір моделі, RSS, холодний старт, час на кліп. Вихід: цифри в цьому документі замість оцінок, рішення A1/A2, рішення §7. Go/no-go за R6.
- **S2. Shadow-режим.** Пасивне збирання ембеддингів власника з PTT-записів у userData. Перевірка працює, але **не блокує** команд, лише логує рішення. Вихід: метрики на реальних даних, false accept/reject, фіксовані пороги.
- **S3. Enforce за opt-in.** Settings-вмикач, блокування wake-команд, мовчазне відсіювання (або відповідно до §9.2). Модель завантажується на кандидата (§6). Вихід: тест на записах, footprint у межах R6.
- **S4. Feedback і повторне навчання.** Правило 15 с (або підтвердження, §9.9). Стирання профілю в Settings. Вихід: тести логіки, ручна перевірка в кімнаті.

Кожен етап — окремий PR. S0 можна робити паралельно з рішенням §7.

## 11. Ризики

- Biometric-подібні дані: профіль лише локально, 0600, видалення в Settings (R5, R10).
- Хибні відмови для власника без пояснення: виглядатиме як «Marshal зламався». Тому §9.2.
- Регрес для Apple engine, якщо обрано варіант 2 в §7.
- Зсув голосу (застуда, гарнітура): пасивне навчання має це ловити; перевірити на S2.
- Ненадійність TTS як негативів: вказано в §5.

## 12. Чого не робимо

- Ідентифікацію, хто саме говорить (кількох людей). Тільки «власник / не власник».
- Розділення мовців у записах дзвінків. Це окрема задача (#295, див. `desktop/meeting/meeting-notes.ts`).
- Хмарну верифікацію голосу.
- Перевірку PTT-диктовки.

## 13. Рішення, прийняті в S0

Власник може змінити кожне: усі числа лежать у `CalibrationParams`.

- **§9.2 і R7, перевірка недоступна.** Команда проходить (`accept`, причина `unavailable` або `not-calibrated`), викликач логує. Мовчки губити команду власника через збій моделі гірше, ніж пропустити чужу. Відмова — лише за балом нижче порогу або за тихим кліпом.
- **§9.6, синтетичні негативи.** Дозволені як стартове калібрування; результат несе `optimistic: true`.
- **§9.8, ціль помилок.** Поріг придатний, лише якщо відсіює ≥ 98 % чужих семплів (false accept ≤ 2 % з §2). Стартова точка — 5-й перцентиль балів власника мінус 0.05.
- **§9.9, feedback.** Пасивне правило 15 с з issue, але відмову хибною робить лише команда, що доведено належить власнику: клавіша або голос, який перевірка прийняла. Повторні відмови поріг не рухають. Крок 0.02, не нижче ніж калібрований поріг мінус 0.1.
- **§9.10, повторне навчання.** Логіка лише повертає `relearn` після трьох хибних відмов за 7 днів. Хто діє (автоматично чи кнопка) — рішення S4.
- **Тихий голос.** Кліп на 15 dB нижче медіани рівнів власника — фон. Фільтр мовчить, поки рівнів менше десяти.
- **A1 проти A2 (частина S1).** `libsherpa-onnx-c-api.dylib` v1.13.8, який уже ставить wake, експортує `SherpaOnnxCreateSpeakerEmbeddingExtractor`, `…CreateStream`, `…IsReady`, `…ComputeEmbedding`, `…Dim` (перевірено `nm -gU` на встановленому runtime). A1 можливий без нового runtime. Структури конфігурації в `sherpa-kws.h` не додані й не звірені; розмір моделі, RSS, холодний старт і час на кліп не заміряні.
