# Scheduled workflows (#280)

Статус: spec, без коду. Епік: #275. Бюджет: #281 (idle ≤ 300 МБ, без моделі в пам'яті, без Python, без поллерів у простої).

Workflow — це повторюваний запуск Claude Code у неінтерактивному режимі (`claude -p`) за розкладом, який людина описала словами. Результат озвучується, показується нотифікацією і йде в графіки. Запуски відбуваються локально, тобто з локальними MCP-серверами і під логіном власника, на відміну від cloud routines (`/schedule`).

## 1. Механізм розкладу

### Рішення

**Один таймер у процесі Marshal, перевзводиться на найближчий запуск.** Не 20-секундний tick із cron-matcher-ом, як у тексті #280.

Причини:
- Tick кожні 20 с робить пробудження CPU ~4 300 разів на добу навіть тоді, коли жодного workflow немає. Це суперечить правилу «жодних поллерів у простої» (#281).
- Уже є прецедент: update check (`desktop/main.ts`, `updateCheckTimer`) та tray refresh (`trayRefreshTimer`, 5 с). Вони стоять у списку на зменшення, а не зразок для нових фіч.

Алгоритм:
1. Будь-яка зміна набору workflow (створення, редагування, увімкнення, вимкнення, видалення) або подія `powerMonitor` `resume` викликає `rearm()`.
2. `rearm()` знаходить найближчий `nextRunAt` серед увімкнених workflow і ставить один `setTimeout` до нього (`unref()`).
3. Коли таймер спрацьовує: запускається workflow, `nextRunAt` для нього перераховується, потім `rearm()`.
4. Немає жодного увімкненого workflow → таймера немає. Idle-внесок нуль.
5. Максимальна затримка одного `setTimeout` в Node обмежена (~24.8 доби). Якщо `nextRunAt` далі, таймер ставиться на `min(nextRunAt, now + 1 доба)` і перевзводиться.

Розклад зберігається як cron-подібне правило (`minute hour dom month dow`) разом із часовим поясом. Розбір мови («щоранку о 9», «кожну годину») — задача моделі при побудові definition (див. розділ 3), а runtime отримує лише вже валідний cron. Час беремо в локальному часовому поясі Mac, зберігаємо його назву (`Europe/Kyiv`), щоб зміна поясу в системі не зсувала запуски мовчки.

### Альтернатива: launchd agent

`launchd` з `StartCalendarInterval` дає два плюси: запуск після сну (launchd збирає пропущені календарні запуски і виконує їх один раз після пробудження) і роботу, коли Marshal закритий.

Чому не обираємо як основний шлях:
- Marshal уже свідомо не веде launchd plist: `desktop/settings-store.ts` і `applyLaunchAtLogin` (`desktop/main.ts`) користуються `app.setLoginItemSettings`, і коментар прямо каже «no launchd plist to maintain».
- Workflow потребує MCP-серверів, озвучки, нотифікацій і черги з presence-гейтами. Усе це живе в процесі Marshal. Окремий launchd-процес мусив би підняти весь цей стек або працювати без нього, і тоді результат не можна озвучити.
- Другий планувальник = другий набір правил (дозволи, `PATH`, `ANTHROPIC_*` з env, #322), які треба тестувати окремо.

Launchd лишається запасним варіантом, якщо знадобиться запуск при закритому Marshal. Це окреме рішення власника, не частина першого етапу.

### Поведінка при сплячому Mac

- Node-таймер під час сну не спрацьовує вчасно. Після `resume` він спрацьовує одразу або з запізненням, залежно від ОС.
- На `powerMonitor` `resume` робимо `rearm()` і перевіряємо пропущені запуски: для кожного увімкненого workflow, чий `nextRunAt` минув.
- Політика пропущеного запуску (за замовчуванням):
  - Пропуск менший за `catchUpWindow` (30 хв) → запуск один раз одразу після пробудження. Інші пропущені запуски того самого workflow зливаються в один.
  - Пропуск більший за `catchUpWindow` → запуск не робиться, у журнал пишеться `skipped: slept`, `nextRunAt` ставиться на наступний слот. Для «щоранку о 9» це правильно: звіт о 16:00 застарів.
- Ця політика є полем workflow (`catchUp: "once" | "skip"`), щоб власник міг вибрати. За замовчуванням `once` для розкладів «раз на години» і `skip` для розкладів «раз на добу» (звіт вранці, спізнений удень, нікому не потрібен).
- Уві сні (асистент `sleeping`, #375) запуски відбуваються, але нічого не озвучується. Результат іде в журнал і показується вікном при пробудженні асистента.

### Поведінка при закритому Marshal

- Поза процесом workflow не запускаються. Пропущені запуски за час, поки Marshal закритий, не відновлюються. При старті діє та сама політика `catchUp`, що й після сну. Старт Marshal рахується як `resume`.
- Опція «запускати при старті» з #280 реалізується тим самим механізмом: при старті для workflow з `runAtStart: true` ставиться `nextRunAt = now`.

## 2. Збої, таймаути, перекриття

- **Один запуск на workflow одночасно.** Якщо попередній ще працює, новий запуск пропускається з записом `skipped: overlap`. Черги з накопиченням немає.
- **Таймаут.** Кожен запуск має `timeoutMs` (за замовчуванням 10 хв). Після нього процес `claude -p` вбивається (SIGTERM, потім SIGKILL через 5 с). Запис: `failed: timeout`.
- **Помилка процесу** (ненульовий код, порожній вихід, невалідний JSON на виході контракту розділу 5): запис `failed: <категорія>` з останнім рядком stderr, обрізаним до 500 символів. Повтор один раз через 2 хв. Другий збій → `failed`, `nextRunAt` стає звичайним наступним слотом.
- **Авторизація.** Якщо процес повертає ознаку «не залогінений» (код `401`, текст про login), workflow ставиться на паузу (`paused: auth`), нотифікація «потрібен вхід у Claude Code». Повторні спроби до дії власника не робимо. Це та сама межа, що для `dontAsk` і дозволів.
- **Серійні збої.** Три поспіль `failed` → workflow вимикається (`paused: failing`), нотифікація з останньою помилкою. Без цього поламаний workflow тихо палив би ліміти кожні 10 хв.
- **Ліміти й ціна.** Поле `maxRunsPerDay` (за замовчуванням 24) — запобіжник від помилкового розкладу «кожну хвилину». Перевищення → `skipped: daily-cap`.
- **Немає мережі / немає Claude Code.** Перед запуском перевіряємо наявність бінарника (той самий шлях, що для асистента, `MARSHAL_CLAUDE_BIN`). Відсутній → `failed: missing-binary`, без повторів.

Таймаути й повтори не реалізуються через `setInterval`. Повтор теж планується через той самий `rearm()`.

## 3. Збереження definition

### Формат

Одна JSON-структура на workflow, збережена в `<userData>/workflows/definitions.json` (масив, версія схеми поля `schemaVersion: 1`):

```json
{
  "id": "wf_01J…",
  "name": "Нові issues у marshal",
  "enabled": true,
  "schedule": { "cron": "0 9 * * *", "timezone": "Europe/Kyiv" },
  "catchUp": "skip",
  "runAtStart": false,
  "timeoutMs": 600000,
  "maxRunsPerDay": 24,
  "model": "haiku",
  "prompt": "…",
  "allowedTools": ["mcp__github__list_issues"],
  "mcpServers": ["github"],
  "writes": false,
  "charts": [],
  "language": "uk",
  "promptHash": "sha256…",
  "createdAt": "…",
  "updatedAt": "…"
}
```

Чому такий склад:
- `allowedTools` — точний список імен, без маски. `--allowedTools` приймає список імен, тож без маски розширити доступ без зміни definition неможливо.
- `promptHash` і хеш списку інструментів використовуються для правила «пам'ять скидається при зміні prompt або списку інструментів» (розділ 5).
- Немає полів для секретів. MCP-сервери адресуються іменем з конфігурації Claude Code. Токени лишаються там, де їх зберігає Claude Code.

### Пам'ять і журнал

- Пам'ять (`memory`) зберігається окремо: `<userData>/workflows/memory/<id>.json`. Її перезапис відбувається разом із успішним запуском, атомарно (tmp-файл і `rename`). Так зламаний запуск не псує попередню пам'ять.
- Журнал запусків: `<userData>/workflows/runs/<id>.ndjson`, один рядок на запуск: час, статус, тривалість, `say`, короткий підсумок `charts`, код помилки. Тіло виводу повне зберігається лише для останніх 20 запусків, решта лишає рядок без тіла. Ліміт файлу: 2 МБ, ротація.
- Усе в `<userData>`. Не в `settings.json`: definitions і журнал ростуть, а settings читається й пишеться цілком при кожній зміні.
- Запис атомарний: `*.tmp` + `rename`, як у `desktop/capture/capture-archive.ts`. Пошкоджений JSON при читанні → файл переносити в `*.corrupt-<ts>` і стартувати з порожнього списку з попередженням. Мовчки стирати не можна.

### Чим не є

- Не cloud routine: нічого не вантажиться в Anthropic-акаунт.
- Не Claude Code `schedule` skill: він створює віддалені agents і не знає про локальні MCP.

## 4. Нотифікації та озвучення

Канали, по порядку важливості:

1. **Озвучення** (`SpeechService.speak`, `key: "workflow:<id>"`), лише якщо `speechEnabled`. Черга вже вміє замінювати невимовлену фразу з тим самим `key` (#266), тож дві пропущені фрази одного workflow не накопичуються.
2. **Нотифікація Electron** з текстом `say` і кнопкою/кліком у вікно асистента, де видно журнал.
3. **Рядок «Останнє»** у вікні асистента (`pushLine`, #284).

Правила:
- Тихі запуски (`say` порожній або `"silent": true` у виводі) лишають лише журнал і рядок «Останнє». Звук не грає ніколи для «нічого не змінилось».
- Під час дзвінка (presence, #267) і запису зустрічі/субтитрів озвучення й нотифікації затримуються в черзі і показуються при виході з дзвінка. Це та сама черга, що для `waiting` (#359). Затримка без ліміту часу небезпечна, тому: після 60 хв черга скидається, а сам результат лишається в журналі.
- Уві сні озвучення немає, журнал і рядок «Останнє» працюють.
- Помилки (`failed`, `paused`) завжди йдуть нотифікацією, навіть на дзвінку, але без озвучення. Тиха помилка гірша за шум.
- Мова озвучення і тексту: `language` поля workflow, за замовчуванням з `assistantLanguage` (#330).

## 5. Вихідний контракт запуску

Кожен запуск — `claude -p` із `--output-format json` і `--json-schema` для контракту:

```json
{ "say": "…", "memory": {…}, "charts": [ … ], "silent": false }
```

- `say` — короткий текст, який озвучується. Ліміт 400 символів, довше обрізається, а не відкидається.
- `memory` — будь-який JSON-об'єкт, розміром ≤ 64 КБ. Передається в наступний запуск як дані, не як інструкція.
- `charts` — масив специфікацій графіків для dashboard-у (#279). Специфікація не містить HTML, тільки дані й тип.
- Невалідний контракт → один повтор із текстом помилки валідатора (той самий механізм, що для побудови definition). Другий невалідний → `failed: contract`.

Пам'ять скидається, якщо змінився `promptHash` або список `allowedTools`. Старий стан більше не є «тим самим завданням», і його видача могла спиратись на інший промпт.

## 6. Безпека доступу

- **Лише читання за замовчуванням.** Інструмент дозволяється, якщо його ім'я містить читальне дієслово (`get`, `list`, `read`, `search`, `query`, `fetch`) і не містить записувального (`create`, `update`, `delete`, `write`, `send`, `post`, `merge`, `close`, `set`). Це перевірка при збереженні definition, а не при запуску.
- Записувальний доступ (`writes: true`) вмикається лише кліком у вікні Marshal. Локальний HTTP API (той самий loopback, що hooks) відкидає будь-який запит із полем `writes`, якщо `Origin` не є origin вікна асистента. Тобто ні веб-сторінка, ні модель не можуть самі собі його видати.
- `--permission-mode dontAsk` з `--allowedTools`: усе, чого немає в списку, відхиляється без запиту, бо немає кого питати.
- Перевірка через PreToolUse, яку вже планує #278 (guard для git і rm). Її використовує і цей шлях, а не окрема копія.
- Процес запуску отримує env без `ANTHROPIC_*` (#322), щоб білінг лишався на підписці, і без session env Claude desktop (#388).

## 7. Побудова definition

- Модель отримує текст користувача і повертає definition за схемою. Валідатор перевіряє: cron валідний, `allowedTools` існують у конфігурації MCP, немає записувальних інструментів без `writes`, `timeoutMs` і `maxRunsPerDay` у межах, `prompt` не порожній.
- Невалідно → один повтор з текстом помилки валідатора. Після другої невдачі UI показує причину і не зберігає.
- Розклад словами («щоранку о 9», «кожну годину») → cron. Невизначений розклад («іноді») не вгадується, а питається одним уточнювальним питанням.
- Джерела для побудови: текст, збережений шаблон dashboard-у (#279), картка з дошки (#276), ідея автоматизації (#273).

## 8. Поетапна доставка

**Етап 0 (цей документ).** Spec, без коду.

**Етап 1. Ядро без моделі.** Файл definitions і журнал, `rearm()` з одним таймером, `catchUp` після сну і старту, перекриття, таймаут, `maxRunsPerDay`, read-only фільтр інструментів, валідатор cron і allowlist. Побудова definition — вручну (JSON у тесті). Тести: матчер і `nextRunAt` (включно з перетином DST), політика `catchUp`, фільтр інструментів, атомарний запис і відновлення пошкодженого файлу, правило скидання пам'яті.

**Етап 2. Побудова з тексту.** Модель будує definition, валідатор і один повтор. Тест: набір фіксованих фраз → очікуваний cron (без живої моделі, через fixture-відповіді).

**Етап 3. Вихід і сповіщення.** Контракт `{say, memory, charts, silent}`, озвучення через чергу з `key`, гейти дзвінка і сну, нотифікації, рядок «Останнє». Перевірка наживо: один реальний workflow спрацьовує за розкладом і говорить результат.

**Етап 4. Записувальний доступ і UI.** Кнопка `writes` у вікні з обмеженням origin, вікно Workflows (вмикач, запуск зараз, розклад словами, модель, журнал, графіки), перевірка footprint через `npm run perf:footprint` (знімок idle з одним активним workflow і після запуску).

Критерій «Done» з #280 виконується після етапу 3. Етап 4 не блокує першу користь.

## 9. Відкриті питання для власника

1. **Запуск при закритому Marshal.** Достатньо, щоб пропущені запуски були лише під час роботи застосунку (поточне рішення), чи треба launchd agent? Друге — окремий план з власним набором правил.
2. **Модель за замовчуванням.** Haiku для щоденних зведень, Sonnet/Opus для аналізу? Пропоную `haiku` за замовчуванням, інші — явний вибір.
3. **Політика `catchUp` для розкладів «раз на години».** Один запуск після сну (пропоную) чи пропуск?
4. **Ліміт нагадувань на дзвінку.** 60 хв черги — достатньо, чи скидати одразу після закінчення дзвінка?
5. **Бюджет запусків.** `maxRunsPerDay: 24` за замовчуванням і глобальний ліміт на всі workflow — потрібен глобальний?
6. **Вибір MCP-серверів.** Чи дозволяти лише ті сервери, що вже налаштовані в Claude Code, чи Marshal має окремий реєстр?
7. **Перевірка «сон → пробудження» наживо.** Node-таймер після сну поводиться по-різному на різних версіях macOS. Перш ніж покладатися на `catchUp`, треба заміряти: поставити таймер на +2 хв, закрити кришку на 5 хв, перевірити час спрацювання. Це вимагає власника біля Mac.
8. **Чи потрібні графіки в першому етапі.** Без `charts` етап 3 простіший; залежність від #279 можна відкласти.

## 10. Що НЕ входить у цей spec

- Код, нові файли поза цим документом, зміни `desktop/main.ts`.
- Launchd plist.
- Cloud-виконання (це `/schedule`, не ця фіча).
- Диспетчеризація голосом «зупини workflow X» — це окрема команда в `./marshal`, її додасть етап 3 за тим самим шаблоном, що `do`.

## 11. Вплив на бюджет (#281)

- Без увімкнених workflow: нуль таймерів, нуль читань файлів у простої.
- З увімкненими: один `setTimeout` і читання `definitions.json` лише при `rearm()` (не за таймером).
- Запуск `claude -p`: окремий процес, у бюджет idle не входить, але пік треба заміряти (`perf:footprint`), як для диктовки.
- Журнал і пам'ять: кілька кілобайт на workflow, ротація не дає зростати безмежно.
