# Voice slide decks — план (issue #277)

Статус: spec, код не змінено. Епік: #275, фаза 4. Цей документ описує потік від голосу до слайдів, формати виводу, двомовність, ресурси, етапи поставки і відкриті питання. Реалізація — окремі PR за етапами нижче.

## Мета

Сказав «зроби 5 слайдів про релізи Marshal за жовтень» — Marshal будує deck у вікні, яке видно під час побудови, дає його презентувати на весь екран, озвучити нотатки і експортувати в PDF або HTML.

Не входить у v1: редагування WYSIWYG мишею, спільний доступ між людьми, синхронізація з Google Slides, шаблони з брендом користувача.

## Потік: від голосу до deck

```
голос / текст
  → транскрипт (диктовка або голосова команда, існуючий шлях)
  → dispatcher: намір «deck» + тема + мова + кількість слайдів
  → outline (мала модель, 1 запит): N заголовків + ключові тези
  → генерація слайдів (стрім): JSON-операції, по одній на слайд
  → op scanner: застосовує кожну завершену операцію
  → render: слайд у sanitised-ізоляції, поступово
  → deck у сховищі (userData), вікно deck-а відкрите
  → дії: present / edit голосом / експорт
```

### Крок 1. Намір і параметри

Диспетчер (`desktop/assistant/dispatcher*.ts`) вже маршрутизує команди. Додаємо один намір `deck` з полями: `topic`, `slideCount` (за замовчуванням 5), `language`, `style` (пресет). Без явних параметрів — дефолти, без уточнювальних питань, якщо тема зрозуміла.

Факти для слайдів (релізи, коміти, issues) — необов'язковий крок: модель може отримати `git log` і закриті issues як контекст через той самий шлях, що `#272 standup`. Без цього кроку слайди пишуться лише з теми.

### Крок 2. Outline

Один короткий запит до провайдера summarizer-а (`streamMessages`, Anthropic або OpenAI-compatible). Вихід — JSON зі списком `{ title, bullets[] }`. Outline показується першим, бо це найдешевше місце, де людина може відмовитися від хибного напрямку.

### Крок 3. Live build: op scanner

Модель пише deck як стрім JSON-операцій, наприклад:

```json
{"op":"deck","title":"...","theme":"..."}
{"op":"slide","index":1,"layout":"title","html":"<section>...</section>"}
{"op":"slide","index":2,"layout":"bullets","html":"..."}
```

Scanner (чистий модуль, без Electron) тримає буфер і віддає операцію, щойно закрилась її об'єктна гранка. Напівнаписаний слайд показується «ростучим» через повторний render з throttle (наприклад, не частіше 4 разів на секунду), щоб не перемальовувати деck на кожен токен.

Вимоги до scanner-а (тести обов'язкові):
- операція, розрізана посеред рядка, не застосовується до повного JSON;
- рядки з `}` і `"` всередині `html` не ламають границі;
- екранування (`\"`, `\\`, `\u`) у межах рядка;
- обрив стріму посередині слайда не псує вже застосовані слайди;
- операції з неправильним `index` або невідомим `op` відкидаються з рядком у лог.

### Крок 4. Sanitiser і ізоляція

Вимога з issue: без скриптів, обробників подій і зовнішніх URL. Пропонований шлях — два шари:

1. **Основний: CSP і ізольований контекст.** Слайди рендеряться у вікні з `Content-Security-Policy: default-src 'none'; img-src data:; style-src 'unsafe-inline'; script-src 'none'` і без `nodeIntegration`. Навіть якщо санітайзер пропустить щось зайве, мережі й скриптів не буде. Це і є гарантія.
2. **Другий: санітайзер.** Парсинг через `DOMParser` у renderer, allowlist тегів і атрибутів, видалення `on*`, `javascript:`, `src`/`href` поза `data:`. Без нової залежності, якщо allowlist короткий; якщо ні — розглянути `DOMPurify` (≈20 КБ, чистий JS).

Тести: санітайзер вирізає `<script>`, `onerror=`, `href="javascript:"`, `<img src="https://...">`, `<iframe>`, `<style>@import url(...)`; CSP-перевірка — окремим e2e-кроком.

### Крок 5. Render-ізоляція: shadow DOM чи iframe

Issue описує shadow DOM. Shadow DOM ділить з документом глобальні події, `document`-рівень CSS-змінні й не ізолює скрипти. Пропонуємо **`<iframe sandbox="" srcdoc="…">` всередині вікна deck-а** як основний варіант: окремий origin, без скриптів, без доступу до батьківського вікна. Ціна — один iframe на поточний слайд (не на весь deck). Див. відкрите питання 1.

### Крок 6. Сховище

- Deck зберігається як JSON: `<userData>/decks/<id>.json` (слайди, тема, мова, пресет, метадані, timestamps).
- Не в репо і не в `~/Screenshots/` (це артефакти, не скріни).
- Ліміт: 50 decks або 100 МБ, найстаріші видаляються тільки після явного підтвердження в UI (не тихо).

## Формати виводу

| Формат | Як | Залежності | Примітки |
|---|---|---|---|
| **PDF** | `webContents.printToPDF` з прихованого вікна deck-а | немає нової | Electron-native, без headless Chrome. Вікно створюється на експорт і знищується після. |
| **HTML** (self-contained) | Збирається з `slides[].html` і inline CSS теми; зображень немає (їх санітайзер не пропускає зовні) | немає | Найпростіший; відкривається в будь-якому браузері. |
| **Slides artifact** | Claude Artifact type «Slides» (`quickstart` з `intent: slides`) | Поза репо, це інструмент Claude Code, не runtime застосунку | Публікація на claude.ai — **зовнішня дія**, потребує явного «так» власника. У застосунку Marshal цього шляху немає; доступний лише сесіям Claude Code, які будують deck за запитом. |
| **pptx** | Skill `anthropic-skills:pptx` (поза репо) для Claude Code; в застосунку — JS-бібліотека на кшталт `pptxgenjs` | у застосунку — нова залежність (JS, без Python) | Python-рантайм заборонений бюджетом #281. Тому in-app pptx — лише якщо власник погодить залежність. Див. питання 2. |

Рекомендація v1: **PDF і HTML** (жодних нових залежностей). Slides artifact — для сесії Claude Code, не для кнопки в застосунку. pptx — після рішення про залежність.

## Presenter

- Окреме fullscreen-вікно, `alwaysOnTop` не потрібен, бо LSUIElement-вікно можна підняти через `app.focus({ steal: true })` (правило з CLAUDE.md, #168).
- Навігація: стрілки, Space, Esc; номер слайда внизу.
- Світла тема для проектора (дозволено issue), вибір на старті.
- Нотатки спікера — друге текстове поле на слайд; показуються тільки в режимі презентера, не в fullscreen.
- Озвучення нотаток: існуючий `speechService.speak(text, { lang, key: 'deck:<id>:<slide>' })`. Черга й мовчання на дзвінку — уже в `SpeechService`, нічого нового.

## Редагування

- Голосом: «слайд 3 коротше», «поміняй 2 і 4», «додай слайд після 1». Диспетчер передає `deck-edit` з індексом і командою; модель повертає одну операцію `slide` або `reorder`. Одна операція — один запит, без перебудови всього deck-а.
- Вручну: текстове поле заголовка і bullets; HTML-редактор не потрібен у v1.
- Кожна зміна — новий запис історії (undo на 10 кроків у пам'яті).

## Дані в слайдах

Слайди з даними (кількість релізів, закриті issues) — фоновий крок: зчитати `git log` / GitHub issues через `gh` (вже використовується в проєкті), перемалювати тільки слайд з `data-source`. Не в v1; залежить від #272 `collectCommits`. Мережа тільки на цьому кроці і тільки з явно дозволених джерел.

## Двомовність

- **Мова deck-а** = мова запиту за замовчуванням (`auto` → мова транскрипту, як у `#272` standup), з перемикачем `uk` / `en` у налаштуваннях deck-а. Змішаний запит — мова, яка переважає в транскрипті.
- **Мова інтерфейсу** (`assistantLanguage`, #330) не змінює мову контенту deck-а.
- Шрифти: системні (SF / Helvetica Neue мають кирилицю). Жодних завантажуваних шрифтів у v1.
- Озвучення нотаток: `lang` на слайд; для української — Piper або Holos (за налаштуванням #325/#333), інакше `say`.
- Модель: без жорсткого «тільки англійською». Промпт вимагає мову з параметра, а не з теми.

## Ресурси (гейт #281)

Бюджет: idle ≤ 300 МБ, без моделей у пам'яті, без Python.

- **Генерація** — віддалений запит, локальної LLM немає. Пам'ять: буфер scanner-а (одна операція, десятки КБ).
- **Вікно deck-а** відкрите лише поки його видно або експортують. Закриття = знищення вікна (як home і віджет). Idle-внесок: 0.
- **Render** — один iframe на поточний слайд, превʼю-мініатюри лише коли список слайдів відкритий; мініатюри — один раз на слайд, не на кожен кадр.
- **PDF** — тимчасовий renderer на 1–3 с, пік приблизно як окремий `renderer` (десятки МБ). Знищується після експорту.
- **Сховище** — JSON, ≈50–200 КБ на deck; ліміт 100 МБ.
- **Замір:** `npm run perf:footprint` на idle і на час побудови 5-слайдового deck-а; знімок — у PR етапу 2 і 3.

Ціль: побудова 5 слайдів без жодного постійного процесу; відкрите вікно deck-а ≤ 150 МБ footprint додатково (оцінка, не заміряно).

## Етапи поставки

**Етап 0 — цей документ.** Рішення, відкриті питання, без коду.

**Етап 1 — чисті шари, без UI.**
- `desktop/decks/op-scanner.ts` — парсер стріму операцій, тести на часткових потоках.
- `desktop/decks/sanitize.ts` — allowlist + тести на вектори з кроку 4.
- `desktop/decks/deck-model.ts` — типи, валідація, збірка HTML і self-contained export.
- `desktop/decks/deck-store.ts` — JSON-сховище, ліміт, retention.
- Готово, якщо `npm run check` зелений, тести покривають вектори з issue.

**Етап 2 — генерація і live build.**
- Намір `deck` у диспетчері, outline, стрімова генерація, вікно deck-а з ростучим слайдом, iframe-render.
- Готово, якщо реальний 5-слайдовий deck будується на голос і видно кожен слайд по мірі появи; замір footprint у PR.

**Етап 3 — presenter і PDF/HTML.**
- Fullscreen presenter, навігація, нотатки, експорт PDF (`printToPDF`) і HTML.
- Готово, якщо PDF відкривається і містить 5 сторінок з кирилицею (перевірка вручну на Mac).

**Етап 4 — редагування голосом і вручну.**
- `deck-edit`, reorder, undo.

**Етап 5 — озвучення нотаток.** `speechService` з `key` на слайд.

**Етап 6 — дані в слайдах** (після #272 `collectCommits`).

**Етап 7 — pptx**, якщо власник погодить залежність (питання 2).

Кожен етап — окремий PR з `Refs #277`; закриття issue — після етапу 3 (ядро з issue) і окремо відмічені етапи 4–6.

## Критерії приймання (з issue)

- op scanner покритий тестами на часткових потоках;
- санітайзер доведено тестами: скрипти і URL вирізаються;
- реальний 5-слайдовий deck будується, презентується і експортується в PDF;
- двомовність: uk і en запит дають відповідну мову контенту і нотаток.

## Відкриті питання

1. **Ізоляція: iframe sandbox чи shadow DOM.** Рекомендація — iframe `sandbox=""` з CSP. Issue каже shadow DOM; потрібне рішення власника, бо це змінює дизайн render-шляху.
2. **pptx в застосунку.** Чи дозволена JS-залежність (`pptxgenjs` або подібна) заради pptx, чи pptx лишається тільки в Claude Code через skill. Python-рішення відхилено бюджетом.
3. **Slides artifact.** Чи потрібна кнопка «опублікувати в Claude» з застосунку. Рекомендація — ні: це зовнішня публікація на claude.ai, її робить сесія Claude Code за явним проханням.
4. **Модель генерації.** Haiku (швидко, дешево) чи Sonnet/Opus для якості тексту слайдів. Вплив на латентність live build: треба заміряти на обох.
5. **Джерела фактів для data-слайдів.** Лише `git` і GitHub через `gh`, чи також Slack/Notion (тоді — окреме рішення про доступи й identity).
6. **Ліміт сховища** — 50 decks / 100 МБ: достатньо чи інакше.
7. **Ліцензія шаблонів пресетів.** Пресети пишемо самі (8–12), без чужих тем.
