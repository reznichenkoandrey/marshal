# Remote Claude Code sessions (SSH / Tailscale)

Статус: етап 1 (read-only список через ssh exec) реалізовано в `desktop/claude-code/remote-source.ts`, на живому хості не перевірено; етапи 2–4 не розпочато. Issue: #288 (exploratory, `priority:low`). Епік: #275, Phase 5.

Мета: бачити й керувати сесіями Claude Code, що працюють на іншій машині (dev-сервер, другий Mac), поряд з локальними. Ім'я в registry — `name@host`.

Нижче — що в поточному коді припускає локальний хост, які транспорти можливі, модель безпеки, етапи доставки і відкриті питання. Усі посилання на код — на стан `main` (c49215d).

## 1. Що ламається для віддалених сесій

Кожен пункт — місце, де код вважає, що сесія живе на тому самому Mac, що й Marshal.

| Місце | Припущення | Чому не працює віддалено |
|---|---|---|
| `desktop/claude-code/registry.ts:39` | Сесії читаються з `os.homedir()/.claude/sessions/<pid>.json` | Файлів на віддаленій машині Marshal не бачить. Потрібен читач через ssh або relay. |
| `registry.ts:93-95` (`isAlive`) | `process.kill(pid, 0)` | Pid віддаленої машини не має сенсу локально. Liveness має перевіряти віддалений бік. |
| `registry.ts:141` | `deps.exists(socketPath)` — звичайний `fs.existsSync` | Сокет `messagingSocketPath` лежить на віддаленій FS. Потрібна перевірка через віддалений бік або форвардинг сокета. |
| `focus.ts` (`focusSession`, `parseProcessTable`, `terminalTabScript`) | `ps -axo`, tty, AppleScript по Terminal/iTerm, `open -a` | Клік «відкрити сесію» на віддаленій сесії не може підняти вкладку на іншій машині. Для неї потрібен інший механізм (tmux attach або інструкція). |
| `reply.ts` | Відповідь вставляється як ввід власника: `focusSession` → ⌘V → Return через AX/Accessibility | Вставка йде в локальний фокус. Для віддаленого терміналу ввід має йти через tmux `send-keys` або через транспорт сесії. Ключовий принцип `reply` («сесія приймає лише ввід власника») треба зберегти, інакше зламається безпека. |
| `hook-installer.ts` | Hooks пишуться в `~/.claude/settings.json` **локального** користувача і вказують на скрипт `<userData>/claude-code/marshal-claude-hook.sh` | На віддаленій машині потрібен свій скрипт і свій `settings.json`. Шлях до скрипта теж локальний. |
| `hook-events.ts` (`buildHookScript`) | Скрипт шле POST на `127.0.0.1:<port>/claude-code/hook`, токен у `auth-header`, файли порту й токена в `userData` (0600) | Порт і токен на віддаленій машині не відповідають Marshal на Mac. Без тунелю або relay події з віддаленого хоста не доходять. |
| `hook-service.ts:45` | Перевірка `req.host === 127.0.0.1:<port>` | Коректна для локального сервера. Для тунелю треба інший Host (або перевірка на боці тунелю). Не послабляти, а явно описати. |
| `hook-service.ts:96` | `server.listen(0, "127.0.0.1")` | Так і треба: сервер не має слухати зовні. Тунель має прив'язуватися до loopback з обох боків. |
| `permission-voice.ts` (hook `PermissionRequest`, `timeout: 60`) | Синхронний hook на віддаленій машині має дочекатися відповіді від Marshal | Відповідь іде через тунель: додаткова латентність і точка відмови. Якщо тунель мертвий, поведінка має бути та сама, що «Marshal не запущений»: порожній stdout, діалог у сесії. Помилка ніколи не дозволяє дію. |
| `dossier.ts`, `answer-summary.ts`, `readRecentTurns` (peek) | Transcript читається з `~/.claude/projects/<cwd>/<sessionId>.jsonl` локально | Transcript віддаленої сесії лежить на віддаленій машині. Читання = передача вмісту розмови через мережу. Це окреме рішення про приватність (див. §3). |
| `context-router` / `claudeCodeRoutingRoots` | Дозволені теки — локальні абсолютні шляхи (`~/htdocs/...`) | Шлях на віддаленій машині має інший префікс. Правило «дозволені теки» має бути прив'язане до `host`, інакше сесія з чужої теки на іншому хості пройде перевірку. |
| `dispatcher.ts:97` (`SOCKETS_DIR`, `uds:<socketPath>`) | `SendMessage` через `uds:` до локального сокета | Віддалений сокет доступний лише через форвардинг UDS (`ssh -L` з `StreamLocal`) або через relay. |
| `dispatcher-files.ts` | Диспетчер і `general` — локальні сесії, права через `permission mode` локального застосунку | Сесія на віддаленому хості працює під правами віддаленого користувача. Режим дозволів, який бачить власник, на віддаленій машині не контролюється Marshal. Це треба явно показувати в UI. |
| `speech` / `say` / `afplay` / Holos / Piper | Озвучення на Mac власника | Не змінюється: мова й голос лишаються локальними (добре). Але «мікрофон на дзвінку» (`mic-users`) дивиться лише локальний аудіо-стан. |
| `registry` і sessions у home (#284) | Список сесій читається лише поки вікно відкрите (`fs.watch` на `~/.claude/sessions`) | Віддалений список треба або опитувати на вимогу (не таймер, #281), або отримувати через відкритий канал relay. Поллера в простої не додавати. |
| `harbor.ts`, `desktop-session.ts`, deep link `claude://code/continue` | Сесія відкривається локально в Harbor або Claude desktop | Для віддаленої сесії відкриття = tmux attach в локальному терміналі через ssh (`ssh -t host tmux attach`) або повідомлення «відкрий на хості». |

Висновок: більшість модулів не треба переписувати. Треба додати шар «джерело сесій» з двома реалізаціями (локальна і віддалена) і прив'язати `host` до сесії, дозволених тек, focus і reply.

## 2. Транспорти

Варіанти, від найпростішого до повного.

### A. Read-only через ssh exec (без встановлення)
`ssh <alias> 'cat ~/.claude/sessions/*.json'` плюс перевірка сокетів. Нічого не ставиться на віддалену машину.
- Плюс: нуль встановлення, нуль відкритих портів, працює з будь-яким `~/.ssh/config`.
- Мінус: немає hook-подій (Stop, Notification, PermissionRequest). Дізнаємося про стан лише при опитуванні. Це узгоджується з #281 (без таймерів), але «чекає дозволу» з віддаленої сесії буде з запізненням.

### B. SSH-тунель до relay (основний варіант)
Relay — маленький скрипт на віддаленій машині, що слухає `127.0.0.1` на випадковому порту, віддає список сесій і приймає hook-події. Marshal відкриває `ssh -N -L <localPort>:127.0.0.1:<relayPort> <alias>` (або ControlMaster-сесію, одну на хост).
- Плюс: жодного публічного порту; авторизація SSH вже є; hook-події доходять у реальному часі.
- Мінус: потрібен віддалений скрипт, версіонування і чисте видалення.

### C. Tailscale
Той самий relay, але Marshal ходить до tailnet-адреси напряму, без ssh-тунелю. Авторизація — ACL tailnet плюс токен relay.
- Плюс: без ControlMaster, стабільна адреса з будь-якої мережі.
- Мінус: прив'язка до Tailscale на обох машинах; додатковий залежний сервіс. Relay однаково має слухати лише tailnet-інтерфейс, не `0.0.0.0`.
- Рекомендація: підтримувати обидва, але початково вибирати B (SSH), бо він не вимагає нових залежностей.

### D. tmux як fallback для команд
Якщо relay не встановлено, але на хості є tmux, команда власника йде як `tmux send-keys -t <session> '<text>' Enter`. Стан сесії читається з `tmux capture-pane`.
- Плюс: не потрібен relay і не потрібен доступ до сокета Claude Code.
- Мінус: сесія мусить бути в tmux; немає структурованого статусу (`waiting`/`idle`); `send-keys` підставляє текст у термінал, тож потрібні ті самі гейти, що в `reply` (сесія `idle`, фокус у полі вводу).

### Вибір
Початково: A для списку, B для подій і команд, D як fallback. C — пізніше, якщо користувач уже в tailnet.

## 3. Модель безпеки

- **Жодного публічного порту.** Relay слухає тільки `127.0.0.1` на віддаленій машині. Доступ — лише через SSH-тунель або tailnet ACL.
- **Авторизація — SSH-ключ власника.** Marshal не зберігає паролі й не просить їх. Ключі лишаються в `~/.ssh`.
- **Host key pinning.** Використовувати звичайний `known_hosts`. Зміна ключа хоста = помилка з поясненням, без автоприйняття.
- **Токен relay.** Окремий випадковий токен на хост, 0600, зберігається так само, як `auth-header` локального hook-сервера. Не в `settings.json`, не в логах, не в title чи URL.
- **Встановлення — лише явний клік на кожен хост.** Нічого не ставиться за замовчуванням і не ставиться автоматично при появі нового alias у `~/.ssh/config`.
- **Видалення — повне.** Uninstall прибирає relay, його токен, hooks з `~/.claude/settings.json` на віддаленій машині і стан у `userData`.
- **Версіонування за хешем вмісту.** Relay має хеш; Marshal перевстановлює лише при зміні хешу, і лише після підтвердження.
- **Гейти не слабшають.** `reply` лишається як є: Return лише коли сесія `idle` і фокус у полі вводу (для tmux — ще й `send-keys` тільки в сесію зі статусом `idle`). Повідомлення від іншої сесії ніколи не рахується згодою власника. Диспетчер не отримує права, яких немає в локальних сесіях.
- **Дозволені теки прив'язані до хоста.** `claudeCodeRoutingRoots` доповнюється полем `host`. Без збігу хоста сесія не читається, навіть якщо шлях схожий.
- **Transcript — окреме рішення.** Читання transcript з віддаленої машини (dossier, peek, summary) передає вміст розмови по мережі. За замовчуванням — вимкнено; вмикається окремим перемикачем для кожного хоста. Без нього віддалена сесія показує лише стан (`busy`/`idle`/`waiting`), як для диспетчера в #373.
- **Не логувати адреси й шляхи** віддаленого хоста в лог поза локальним debug-режимом (аналогічно до правила для calendar-URL у #269).
- **Голос.** Озвучування лишається локальним. Текст сесії, що звучить уголос, — той самий, що для локальної сесії, без розширення вмісту.

## 4. Етапи доставки

Кожен етап — окремий PR, зі своїм виміром бюджету (`npm run perf:footprint`) і тестами на fixture-файлах. Жодного живого хоста в CI.

**Етап 0. Документація й ручний варіант (цей документ).** Описати, як налаштувати `~/.ssh/config` і `ssh -L` вручну. Без змін у коді.

**Етап 1. Read-only список віддалених сесій.** Модуль `desktop/claude-code/remote-source.ts`: опитування через ssh exec **на вимогу** (відкриття вікна home або tray-меню), без таймера. Сесії показуються як `name@host` з позначкою `remote`. Жодних дій, жодних змін на хості. Тести — на текстовому виході ssh (fixture).

**Етап 2. Relay і hook-події.** Встановлення relay з явним підтвердженням per host, версіонування за хешем, тунель `ssh -N -L`, події Stop/Notification через тунель, спул на випадок розриву. Видалення повністю прибирає все. Бюджет: тунель і relay не мають таймерів поза подіями; ControlMaster — один на хост.

**Етап 3. Команди власника.** `./marshal reply` і диспетчер для віддаленої сесії: спочатку через форвардинг UDS (якщо relay його віддає), далі fallback на tmux `send-keys`. Гейти ті самі, що локально.

**Етап 4. Перегляд і відкриття.** Peek/dossier для віддаленої сесії — лише після окремого перемикача з §3. Відкриття сесії — `ssh -t <host> tmux attach` у локальному терміналі або інструкція.

Кожен етап можна зупинити без шкоди для локальної роботи. Етап 1 можна випустити без етапів 2–4.

## 5. Відкриті питання

1. **Чи переживає форвардинг UDS.** Чи приймає `messagingSocketPath` Claude Code з'єднання через `ssh -L` (`StreamLocal`) без помилок автентифікації. Перевірити на двох машинах (dev-хост і Mac), не в CI.
2. **Мова relay.** На віддаленому хості може не бути Node. Варіанти: sh+curl скрипт (як hook, без рантайму) або один статичний бінарник. Python на боці Marshal заборонено; на віддаленому хості — рішення власника.
3. **Формат `~/.claude/sessions/*.json` на Linux.** Файли знято з macOS (2.1.317). Чи однаковий формат і поля на Linux — не перевірено.
4. **Латентність permission hook через тунель.** Синхронний hook має 60 с таймаут. Потрібно заміряти, скільки додає тунель, і чи лишається запас для голосової відповіді.
5. **Ідентифікація хоста.** `name@host`: чи брати alias з `~/.ssh/config`, чи hostname з relay. Що робити з двома alias на одну машину.
6. **Права віддаленої сесії.** Режим дозволів віддаленого Claude Code не видно з Marshal надійно. Чи показувати його в UI як окремий стан, чи блокувати голосові дозволи для віддалених сесій взагалі (консервативний варіант).
7. **Tailscale-ACL.** Як мінімізувати доступ: один порт relay, один tailnet-tag на машину. Потрібно уточнити, чи власник використовує Tailscale SSH.
8. **Приватність transcript.** Чи достатньо окремого перемикача на хост, чи потрібен і підтверджений кожного разу показ, який саме вміст піде з віддаленої машини.
9. **Коли це починати.** Issue каже «start only when there is a real remote host in use». Потрібно від власника: чи є зараз постійний віддалений хост з Claude Code, і чи вважати етап 1 достатнім без етапів 2–4.

## 6. Що не входить у цей документ

- Реалізація будь-якого етапу.
- Зміни `desktop/claude-code/*` чи `docs/` поза цим файлом.
- Рішення щодо Windows і Linux-клієнта Marshal (Marshal — macOS-first).
